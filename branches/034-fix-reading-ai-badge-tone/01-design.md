# 034 fix/reading-ai-badge-tone — 설계 문서

## 변경 사유

사용자 결정(2026-10-29, 운영 화면 스크린샷을 보고):

1. 목소리 해설 아래의 긴 안내 문장(`result.readingNote`, "AI가 타입과 여섯 축 수치만 보고 쓴 글이에요. 녹음은 듣지 않았어요.")을 없앤다. 대신 제목 옆에 작은 **"AI"** 표시만 남긴다.
   - 문장을 아예 지우는 안도 있었다. 하지만 한국 AI 기본법(2026-01 시행)에 생성형 AI 결과물 표시 조항이 있는 것으로 알려져 있어(이 서비스에 적용되는지는 불확실, 법률 자문 아님) 작은 표시는 남기는 안을 사용자가 골랐다.
2. 스크린샷의 해설은 "흘러나옵니다·조화롭습니다"(합니다체)와 "느껴져요·돼요"(해요체)가 섞여 있다. 프롬프트는 해요체를 지시하지만 지켜지지 않았다. **한국어 해설의 모든 문장이 해요체가 아니면 출력 계약 위반으로 본다.** 위반이면 031의 계약 재호출(`CONTRACT_RETRIES`)로 Claude를 한 번 더 부른다.

## 해요체 검사

> 아래 의사코드와 표는 처음 설계다. 판정은 1차 리뷰 뒤 '다' 규칙으로, 2차 리뷰 뒤 `…다·…니까·…십시오` 와 문장 속 인용 합치기로 바뀌었다(아래 "1차 리뷰 뒤 바뀐 설계", "2차 리뷰 뒤 바뀐 설계").

```
리딩을 문장 끝 구두점(. ! ? …) 뒤 공백으로 나눈다
→ 각 문장 끝의 구두점·따옴표·닫는 괄호·물결을 떼고
→ 마지막 글자가 '요' 또는 '죠'가 아니면 위반(오류 메시지: "reading style: sentence N is not 해요체")
```

| 결정 | 근거 |
| --- | --- |
| 마지막 글자 '요'·'죠' | 해요체 종결은 …요(…어요, …네요, …군요, …나요, …이에요)와 …죠(…지요)로 끝난다. 합니다체(…니다)와 해라체(…다)를 가른다 |
| 공용 검증(`readingOutput.ts`)에 둔다 | 두 제공자가 같은 계약을 지키게 하는 한 곳이다(010). Workers AI 예비 출력이 섞이면 그 제공자의 실패 → 고정 문구(카탈로그 설명)가 된다. ~~문체가 섞인 글보다 낫다~~ — 그 카탈로그 설명 16개가 모두 섞여 있었다(1차 리뷰 #1). 설명도 해요체로 고쳐 이 근거를 맞췄다 |
| 오류 메시지에 본문을 넣지 않는다 | 로그 규칙(응답 본문 없음). 몇 번째 문장인지만 쓴다 |
| 계약 재호출로 이어짐 | 031에서 만든 경로라 새 코드가 없다. 거부가 아니고 신호가 살아 있으면 Claude를 한 번 더 부른다 |

## 1차 리뷰 뒤 바뀐 설계

사용자 결정(2026-10-29, 1차 리뷰 #1·#9를 보고): 타입 설명도 해요체로 고치고, 초상과 공유 이미지에도 AI 표시를 넣는다.

| 바뀐 것 | 내용 | 근거 |
| --- | --- | --- |
| 타입 설명 16개(`shared/catalog.ts`) | 첫 문장을 해요체로 바꿈. 굽이칩니다→굽이쳐요, 말합니다→말해요, 흐릅니다→흘러요, 이어집니다→이어져요, 오갑니다→오가요, 움직입니다→움직여요, 오르내립니다→오르내려요, 날아오릅니다→날아올라요 | 모델에 "for mood only" 예시로 넣는 글이 16개 모두 "합니다체 + 해요체"였다. 사용자가 본 섞임과 같은 꼴이다. 고치면 화면의 타입 설명(해설이 없을 때 남는 글)도 함께 맞는다 |
| 판정 규칙 | "끝 글자가 요·죠가 아니면 위반" → **"끝 글자가 다면 위반"** | 엄격한 판정은 문장 중간의 물음표·인용 속 반말·이모지 같은 정상 글을 거절했다(1차 리뷰 #4). 사용자가 지적한 합니다체·해라체만 잡는다. 해체(…네)와 명사 종결은 통과한다(README 알려진 한계) |
| 문장 나누기 | 닫는 따옴표·괄호가 붙은 끝 구두점, 전각 `。！？`, `⋯`, `~` 뒤 공백에서도 나눈다. 끝 정리에 전각 구두점과 이모지를 더함 | `.”`·`.)` 뒤의 합니다체 문장이 통과했다(1차 리뷰 #3) |
| 배지 대비 | `.card__badge` 글자 `color-mix(var(--accent) 75%, var(--fg))` | 라이트 3.87:1 → 약 5.5:1(1차 리뷰 #2, 002의 `.howto__num` 과 같은 처리) |
| 초상 AI 표시 | 결과 화면 `PortraitFrame` 의 생성 초상 오른쪽 위에 `.portrait__badge`(어두운 반투명 바탕·흰 글자). 공유 이미지(`renderCard.ts`)의 초상 오른쪽 위에도 같은 알약(`CardLabels.aiMark`) | 실사 인물 이미지가 가장 "실제와 구분하기 어려운" 결과물이다(1차 리뷰 #9, 해석 불확실). 자리표시 초상은 AI가 만든 것이 아니라 붙이지 않는다 |
| 메시지 키 | `result.readingBadge` → `result.aiBadge`(해설·초상·공유 이미지가 함께 씀) | 같은 표시 하나 |

공유 이미지의 캡션(AI 문구)에는 따로 표시하지 않는다. 같은 이미지 안 초상의 표시로 갈음한다(README 알려진 한계).

## 2차 리뷰 뒤 바뀐 설계

| 바뀐 것 | 내용 | 근거 |
| --- | --- | --- |
| 판정 종결 | '다' → `…다·…니까·…십시오`(`NON_POLITE_ENDING`) | 합니다체 의문·명령("있습니까?", "보십시오.")이 통과했다(2차 리뷰 #11). 해요체는 이 셋으로 끝나지 않는다 |
| 문장 속 인용 | 조각이 그 안에서 연 따옴표를 닫으며 끝나면 다음 조각과 합친다(`splitSentences`) | `목소리가 "반갑습니다." 하고 …` 처럼 정상 해요체가 거절됐다(2차 리뷰 #10, 1차 반영의 부작용) |
| 캡션 옆 AI 표시 | 공유 이미지에서 자리표시 초상이고 캡션이 있으면 캡션 오른쪽에 같은 알약. 캡션과 알약을 한 덩어리로 가운데에 두고, 캡션 폭 한도에서 알약 몫을 뺀다 | 사용자 결정(2차 리뷰 #13): 초상 표시로 갈음할 수 없는 경우 |
| 공유 이미지 표시 글자 | 26px → 30px | 1080px 카드를 폰 폭으로 보면 9px 남짓이었다(2차 리뷰 #14) |
| 화면 안내문 | 합니다체 유지 | 사용자 결정(2차 리뷰 #15): 해요체 규칙은 AI 해설과 모델에 넣는 타입 설명에만 |
